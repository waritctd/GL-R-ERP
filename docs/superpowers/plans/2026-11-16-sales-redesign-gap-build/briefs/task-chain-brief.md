## What to build
### 1. One source of truth for the chain (this is the "up to date with the งาน tab" requirement)
A single server-computed **document chain summary** for a deal/quotation, used by BOTH the quotation page's card and the deal page. It states, for the quotation's deal: whether and when the order was confirmed (and from which quotation); the deposit policy (percent; "no deposit"); the deposit notice's state, number, issue date and whether a draft exists; whether the deposit has been confirmed received; the remaining invoice's state, number and date, whether it can be created now and, if not, the reason as a stable code the frontend turns into Thai; and, for the viewer, which of the chain's actions they may perform (computed by the SAME service methods that enforce those actions, never re-derived).
- Prefer adding this as fields on responses the two pages already fetch, or one small read endpoint both call; choose the smaller change, state it as a sales API contract change, and mirror it in `mockApi.js` with an accurate `// Mirrors <JavaClass>` header.
- The deal page's เงิน tab and "ขั้นต่อไป" card must read the same summary (or be shown, by a test, to agree with it for every state): refactor so the next-step wording and the locked reasons come from one place. The prototype found a pre-existing inconsistency: after confirming the order from the quotation page, the deal page's main button read "บันทึกผลประมูล" and the เงิน tab pointed at a create-notice button that was not there. Reproduce that against the Java service (not just the mock); if it is real, fix it as part of making the two pages agree; if it is a mock-only artefact, fix the mock and say so.
- Freshness: every mutation in the chain (confirm order, create/save/issue deposit notice, save/issue remaining invoice, and finance's confirm-deposit) invalidates the query keys BOTH pages use, so a user who acts on one page and navigates to the other never sees a stale step. Enumerate the mutations and the keys each invalidates in one table in your report, and pin it with tests (act on page A, render page B from the same query client, assert the new state without a manual refetch).
- A rep who has the quotation page open while finance confirms the deposit elsewhere will not see it until refetch: refetch the summary on window focus and when the card becomes visible (use the query library's existing options; no polling loop).

### 2. The card on the quotation page
As approved in the prototype ("เอกสารต่อจากใบเสนอราคานี้", four steps: ใบเสนอราคา → ยืนยันคำสั่งซื้อ → ใบแจ้งยอดเงินรับมัดจำ → ใบแจ้งหนี้ส่วนที่เหลือ), with the owner-approved fixes:
- On a phone, completed steps collapse to ONE line each (check, name, number/date, download icon); only the current step is expanded. The card must not add more than roughly 160px above the document at 375px when two steps are complete.
- The quotation's download appears ONCE: keep the page header's existing download and do not repeat a button in step 1 (step 1 shows number, status and date only).
- The "current step" ring marks only a step the VIEWER can act on now. A step that is waiting on someone else (for example the deposit awaiting ฝ่ายบัญชี's confirmation) is shown as waiting, with who it waits on, not as the viewer's turn.
- Every tap target at least 44px, including the dialog's close button at 320px.
- Exactly one primary button in the card at any time; each issuing action keeps its own confirm with the "cannot be edited after issuing" warning first; nothing is issued in one click.
- Deposit notice from this page: the button creates/loads the server draft, then opens the dialog showing the DRAFT's saved figures (never figures computed in the browser), "แก้รายละเอียด" linking to the full notice page, and "ออกเอกสาร". After issuing: number, date, "ดาวน์โหลด PDF".
- Remaining invoice from this page: opens the existing `RemainingInvoiceDialog`.
- A 0% deposit quotation shows step 3 as "ไม่รับมัดจำ", skipped.
- Which quotation shows the card: an approved quotation that is the one the deal's order was (or can be) confirmed from. For a superseded revision, a quotation of a deal whose order was confirmed from a DIFFERENT quotation, a cancelled quotation, or a deal that is lost/cancelled/paused: show the true situation in one line with a link to the quotation or the deal that carries the chain, never a chain with buttons that would fail. Enumerate these cases and test each.
- Labels say "งาน" where the word appears ("เปิดงาน", not "เปิดดีล", on anything you add).

### 3. The list
Each row of the ใบเสนอราคา list carries one small chain mark from a field the list endpoint returns per row (no per-row extra requests): "รอยืนยันคำสั่งซื้อ", "ยืนยันแล้ว · รอใบแจ้งมัดจำ", "ยืนยันแล้ว · ไม่รับมัดจำ", "ออกใบแจ้งมัดจำแล้ว", "ออกใบแจ้งหนี้แล้ว". Only on rows where it is true and useful (approved, in-force quotations); nothing on drafts, superseded or cancelled rows. It must work in both list views (flat and grouped) and must not break the measured column floors (read the comment block above `LIST_TABLE_GRID`; if a floor must change, re-measure and say so).
